# 実装課題

課題は 4 つあり、順番に取り組みます。あとの課題は前の課題の上に積み上がるため、
先のほうが面白そうに見えても順番どおりに進めてください。

**課題ごとに専用のページがあります。**それぞれのフォルダの中にあり、その課題で
読む資料、シミュレータと実機の違い、合否の判定について書いてあります。まずそこを
読み、次に課題そのもの（その課題の `main.c` の先頭）に進んでください。

このページはビルドと実行のしかたです。**コースの仕組みそのもの** — 採点、1 日の
回数、Releases、返事が来ないときの対処 — は
[`../COURSE.ja.md`](../COURSE.ja.md) にあります。

> この文書には英語版があります: [`README.md`](README.md)

## 始める前に

パソコンのセットアップが必要です。[`../SETUP.ja.md`](../SETUP.ja.md) を参照して
ください。確認は次のコマンドです。

**Windows**

```
powershell -ExecutionPolicy Bypass -File tools\check-environment.ps1
```

**macOS ・ Linux**

```
./tools/check-environment.sh
```

`Ready` と表示されるまでは先に進まないでください。

## ビルドと実行

ボード画面の上部にある **課題のビルドと実行** で課題を選び、ボタンを押して
ください。

講座が採点に使うものと同じビルド（同じスクリプトで、その写しではありません）
でコンパイルし、その結果をボードに読み込みます。入力するコマンドも、移動する
ファイルもありません。

何も書いていない状態でも、ひな形はコンパイルが通ります。ただし何も動きません。
これは意図的です。コンパイルエラーが出たら、それは自分が今入れたものであって、
元からあったものではないと分かるためです。

コンパイルできなかった場合は、ページがコンパイラ自身の出力を表示します。その
上の行を先に読んでください。問題が自分のコードにあるのか環境にあるのかを示して
おり、この 2 つは対処が正反対です。

ビルドは一度に 1 つだけ動きます。実行中にもう一度押した場合、ページはキューに
入れずにその旨を伝えます。ビルドは 1 秒もかからないので、もう一度押してください。

ボード画面は **http://localhost:8000** です。日本語で開きます。英語にするには
`?lang=en` を付けてください。

そこではボタンを押したり、自分のプログラムがシリアルポートに出力した内容を
読んだりできます。右側のパレットから、ボードに載っていない部品（LED の追加、
スイッチ、センサー）を足すこともできます。追加した部品は配線したピンの位置に
描かれ、自分の `board.repl` に書き込まれます。つまり、自分のコードが動く
ボードは、自分が組んだボードです。4 つ目の課題にはセンサーと LED 4 個の両方が
必要で、どちらも自分で追加するまで存在しません。

**GitHub がビルドしたものを実行する。** そのボタンの隣に **GitHub がビルド
したものを実行** があります。直前の push を GitHub がコンパイルした firmware を
取得して読み込みます。結果が納得できないときに、自分が横でビルドしたものでは
なく、機械がビルドしたそのものを動かすためのものです。

どのコミットのビルドかを表示し、いま手元にあるコードと違う場合はそのことを
はっきり伝えます。GitHub がビルドするのは push したものなので、作業中の
コードはたいてい先に進んでいます。

このビルドの保持期間は 7 日です。無い場合は、もう一度 push すれば作られます。

クローンに GitHub の資格情報が保存されていない場合、この操作は使えず、理由が
表示されます。その場合は自分でビルドをダウンロードし、ページにドロップして
ください。同じように読み込まれます。

ここで設定したセンサーの値は、ビルドし直したときも、他から持ってきたビルドを
読み込んだときも保たれます。firmware を読み込むとボード上のすべての部品が
リセットされるため、これがないと 4 つ目の課題では毎回値が失われます。

**コマンドを自分で入力したい場合**、コンテナの中でも引き続き使えます。書いて
あるのは [`NATIVE-SETUP.ja.md`](../NATIVE-SETUP.ja.md) です。これはコンテナを
まったく動かせないマシン向けの手順で、全体がコマンドで書かれています。

## 作業は main.c に書きます

採点に使われるのは `main.c` だけです。その横にヘッダーや
2 つ目の `.c` を追加しても、採点側には**渡りません**。

これは気づきにくい問題です。自分の PC では同じフォルダにあるため
コンパイラが見つけてしまい、ビルドが通ります。採点側には
`main.c` しかないため `#include` の行で止まり、ファイル名を
間違えたようなエラーに見えます。その場合は、使われなかった
ファイル名が返信に記載されます。

補助的な関数を書くのは問題ありません。`main.c` の中で、
使う関数の上に書いてください。

## 与えられるもの、与えられないもの

ひな形が与えるのは、全体の構造、ビルド、スタートアップコード、そして CMSIS
ヘッダ経由のレジスタ**名**です。`GPIOA->` と入力すれば、エディタが候補を
出してくれます。

**値**は与えません。どのビットでクロックを有効にするか、どの値が出力を意味するか、
1 秒にするプリスケーラはいくつか。これらはリファレンスマニュアルにあり、それを
読み解くことが課題そのものです。答えを渡してしまうと、コードは動くけれども次の
課題は書けない、という状態になります。

必要な資料は次の 3 つです。課題ごとのページに、その課題で使うものと、どこを
たどれば開けるかが書いてあります。ここから探し当てる必要はありません。

## シミュレータは実機ではありません

ここでは動くのに実機では失敗することがあり、シミュレータは何も警告しません。
一覧は [`../DIVERGENCES.ja.md`](../DIVERGENCES.ja.md) にあります。課題 4 に
関係するものは、その `main.c` の冒頭にも再掲しています。

この 4 つの課題を越えて自分で試す前に、もう 1 件知っておいてください。
シミュレータは汎用の STM32F4 定義の上に作られているため、**F401RE が持っていない
周辺機器**まで使えてしまいます。Ethernet コントローラ、CAN が 2 系統、GPIO ポート
F から K、UART4 と UART5、そして TIM6、TIM7、TIM8、TIM12 から TIM14 です。これらを
使ったコードはここでは問題なく動きますが、実機では決して動きません。課題で扱って
いない周辺機器を使う前に、データシート（DS10086）で確認してください。
一覧の `superset-peripherals` の項です。

書いたコードが実機の NUCLEO-F401RE で動くと信じる前に、必ず目を通してください。
